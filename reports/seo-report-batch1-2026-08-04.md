### R9. 【新增阻断·影响后续 90 篇】link-strategist 的 B4 规范与 qa_check 检查 8 直接冲突

link-strategist 的 B4 规范要求「后续 90 篇每篇 ≥1 条正文内链」，我的 §6.5 第 3 条也提了同样方向。**但这条规范在当前工具链下会 100% 失败，我们两人此前都没发现。**

实测（内存模拟，未改任何稿件）：

```
构建器 inline() 渲染：  [锚文本](target.html) → <a href="target.html">锚文本</a>   支持 ✅
qa_check 检查 8 判定：  命中「正文手写MD链接」                                    FAIL ❌

给现有 10 篇各加 1 条正文内链后：10/10 全部 FAIL
```

矛盾点：`build_articles.py:172` 的 `inline()` **支持**正文 MD 链接，但 `qa_check.py:71-72` 把它列为**硬失败**。一个支持、一个硬拦。

**但不能简单删掉检查 8。** 它承担着真实的守门职责——强制内链走 front-matter，从而享受两道校验：

1. `build_articles.py:383-385`：目标 slug 不存在时跳过，防死链
2. `qa_check.py:78-84`：path 白名单 + slug 存在性校验

我在 §6.4 把「内链无死链」列为通过项，正是建立在这套校验之上。**直接删掉检查 8，正文内链就会绕过全部校验，死链无人兜底**——对一个要扩到 100 篇的站，这是必然会出事的地方。

**建议改法**：把检查 8 从「禁止」改为「校验」，即允许正文 MD 链接，但逐条验证目标合法性：

```python
# 替换 qa_check.py:71-72
for anchor, href in re.findall(r"\[([^]]+)\]\(([^)]+)\)", nocode):
    tgt = href.split("#")[0].split("?")[0]
    if tgt.startswith(("http://", "https://")):
        continue                                   # 外链另有规范，此处不管
    if tgt in ALLOWED_PATHS:
        continue                                   # 站内白名单路径
    if tgt.endswith(".html") and tgt[:-5] in FILES:
        continue                                   # 指向本批文章
    issues.append("正文内链目标不存在:" + tgt)
```

这样既落地 B4，又保住死链防护。**执行顺序上，qa_check 必须先改，否则第 2 批第一篇稿子就会卡住。**

此项已同步 link-strategist。**归属建议：qa_check 的改动由 team-lead 统一执行，我和 link-strategist 都不单方面改。**

### 1.3 最影响这批内容排名的 3 个问题

**① 全站 13 个页面无一有 canonical 标签（模板级，阻断发布）**
这是唯一真正意义上的阻断项。详见 §6.1。对中文站尤其致命：微信分享会给 URL 追加 `?from=singlemessage` / `?from=timeline`，QQ 追加 `?_wv=`，百度移动端可能追加 `?ivk_sa=`。没有 canonical，这些带参 URL 会被当作独立页面收录，把同一篇文章的权重拆成好几份。新域名本来权重就薄，经不起这种稀释。百度官方明确支持 `rel="canonical"`。

**② 10 篇的 meta_description 全部不含主关键词（内容级，阻断发布）**
实测：10/10 篇的 description 里，主关键词的宽松归一化形式都不存在。百度和 Google 都会对摘要中命中查询词的部分**加粗**，这是移动端 SERP 里最直接的 CTR 杠杆。对一个零外链的新站，排名进不了前三时，CTR 是唯一能自己控制的变量。10 条替换稿见 §4.2，全部已实测落在 145–162 宽度内。

**③ 主关键词以「全小写无空格」硬插正文，与全站排版规范冲突（内容级，建议改）**

实测 9/10 篇的首段第一句直接以裸关键词开头，例如 `ai生成ppt哪个好，先别看模板漂不漂亮`、`ai提示词怎么写，先记住一个诊断结论`。而同一篇文章的 H2、表格、其余正文一律写作「AI 生成 PPT」「AI 提示词」。**同一页面内两套排版规范并存，是最典型的机器塞词痕迹。** 这既伤人工阅读信任（影响停留时长），也直接污染了段落型精选摘要的抓取素材——搜索引擎抓首段做摘要时，展示出来的就是这句小写粘连的句子。详见 §3.2，这是我对「关键词密度口径」问题的正式回应。

### 5.2 明确不建议追加 FAQPage 和 HowTo — 这两类富媒体结果已废弃

任务书点名问是否该加 `FAQPage` / `HowTo`。**我的判断是都不要加，这与常见 SEO 建议相反，依据如下：**

- **FAQPage**：Google 官方文档已挂弃用公告——**自 2026 年 5 月 7 日起，Google 搜索不再展示 FAQ 富媒体结果**；2026 年 6 月移除 FAQ 搜索外观、富媒体结果报告及富媒体测试支持；2026 年 8 月移除 Search Console API 支持。也就是说，**这个功能在两个多月前刚刚下线，本月 API 支持也归零**。此前从 2023 年 8 月起它就已被限制为仅政府和权威医疗站点可见，Learntide 本来也不在适用范围内。加了不会被罚，但零收益。
- **HowTo**：桌面端 2023 年 9 月即废弃，此后所有设备均不再展示，Google 搜索中心已下架该文档。047 / 052 / 041 虽然是标准的步骤型内容，**加 HowTo 也拿不到任何富媒体展示**。
- **ItemList**：009 / 039 / 025 / 034 是清单文，但 `ItemList` 单独使用不产生富媒体结果（轮播需要配合特定场景且要求列表项各有独立 URL）。收益极低，不建议现在投入。

**结论：把本该花在 FAQ/HowTo 上的时间，投到下面两件仍然有效的事情上。**

### 5.3 建议追加：BreadcrumbList（全站 13 页，优先级最高）

`BreadcrumbList` 是目前仍然稳定产出富媒体结果的类型之一，会把 SERP 里的 URL 行替换为「Learntide › 工具测评 › 文章标题」的面包屑路径，视觉上更可信，对新站的品牌认知建立有实际帮助。

**现状：全站无面包屑，既无可见导航也无标记。**

**需要正文配合什么**：Google 要求结构化数据与页面可见内容一致，所以要同时做两件事——

1. 在 `<article>` 内 `<h1>` 之前加一段可见面包屑（可复用现有 `.article-meta` 的样式位）：
   ```html
   <nav class="breadcrumb" aria-label="面包屑">
     <a href="../index.html">首页</a> ›
     <a href="../articles.html">工具测评</a> ›
     <span>DeepSeek 和 ChatGPT 哪个好用？6 个场景对比</span>
   </nav>
   ```
2. 在 `head_extra` 里追加对应 JSON-LD：
   ```json
   {"@context":"https://schema.org","@type":"BreadcrumbList","itemListElement":[
     {"@type":"ListItem","position":1,"name":"首页","item":"https://learntide.cc.cd/"},
     {"@type":"ListItem","position":2,"name":"工具测评","item":"https://learntide.cc.cd/articles.html"},
     {"@type":"ListItem","position":3,"name":"DeepSeek 和 ChatGPT 哪个好用？6 个场景对比"}
   ```

   栏目名直接取 front-matter 的 `category`，最后一级不带 `item`。这是模板级改动，10 篇 + 3 篇 legacy 一次生效。

## 六、技术 SEO 检查

已实测读取全部 13 个 `articles/*.html` 及 `index.html` / `sitemap.xml` / `robots.txt` / `build_articles.py`。

### 6.1 【阻断】canonical 标签全站缺失

**实测结果：13 个 HTML 文件中，含 `rel="canonical"` 的数量为 0。**

根因在 `build_articles.py` 的 `page_shell()`（第 308–350 行），模板从未输出 canonical。

**影响（对本站是实打实的，不是理论风险）**：

1. **中文社交平台的 URL 追参**——微信分享追加 `?from=singlemessage`、`?from=timeline`、`&isappinstalled=0`，QQ 追加 `?_wv=`，部分百度入口追加 `?ivk_sa=`。每一个变体都会被当成独立 URL 抓取收录，同一篇文章的外链权重和点击信号被拆散。这批内容本来就打算靠社交分享冷启动，正好撞在这个坑上。
2. **多访问路径重复**——`https://learntide.cc.cd/`、`/index.html`、以及 http/https、带不带 www 的组合，在没有 canonical 时都可能各自被收录。
3. **新域名容错低**——零外链的站点，权重稀释的相对代价远高于成熟站。
4. 百度官方支持 `rel="canonical"`，Google 更是把它作为主要归一化信号，成本极低、收益确定。

**建议写法**（模板级，一次改完 13 页）：

在 `page_shell()` 增加 `canonical` 参数，并在 `<head>` 内输出绝对 URL：

```python
def page_shell(prefix, active, title, description, head_extra, body,
               og_type="website", canonical=""):
    ...
    # <head> 模板内新增：
    # <link rel="canonical" href="{canon}">
    # <meta property="og:url" content="{canon}">
    # <meta property="og:site_name" content="Learntide 学习潮汐">
    # <meta property="og:locale" content="zh_CN">
```

调用侧传值：

| 调用点 | canonical 值 |
|---|---|
| `render_article()` | `"%s/articles/%s.html" % (SITE_URL, slug)` |
| `render_archive()` | `SITE_URL + "/articles.html"` |
| `index.html`（手写） | `https://learntide.cc.cd/` |
| `tools.html` / `about.html`（手写） | 各自绝对 URL |

**务必用绝对 URL，且与 sitemap.xml 中的写法逐字一致**（都用 `https://learntide.cc.cd/articles/xxx.html`，不要出现结尾斜杠或大小写差异），否则 canonical 与 sitemap 互相打架。

### 6.2 【建议】OG / Twitter 卡片字段不全

实测 13 个页面均缺 `og:url`、`og:image`、`og:site_name`、`og:locale`、`twitter:card`。现有只有 `og:title` / `og:description` / `og:type`。

影响：微信、微博、知乎等平台抓取分享卡片时，无标准缩略图和站点名，卡片观感差，直接影响社交冷启动的点击率。建议随 §6.1 一并在模板补齐，并准备一张 1200×630 默认图。

### 6.3 【建议】标题层级跳级

实测所有文章页的标题序列为：

```
h1 → h4（本文目录）→ h2 → h2 → h2 → h2 → h2 → h4（相关阅读）
```

`<h1>` 之后紧跟 `<h4>`，跳过了 h2、h3。虽然 Google 早已声明标题层级不是排名因素，但这会让文档大纲（document outline）解析异常，对屏幕阅读器和部分内容提取器不友好。

建议二选一（模板级，`build_articles.py` 第 366 行与第 397 行）：

### 7.2 081「大模型是什么」— 段落型，全批最强候选

「大模型是什么」是纯定义型查询，百度和 Google 都极大概率给段落摘要。当前首段：

> 大模型是什么？它是一个读过海量文字、专门预测「下一个词该是什么」的程序。你打出「今天中午我想点一份」，它根据读过的无数句子算出后面最可能跟「外卖」「盒饭」「炒面」，挑一个接上，再猜下一个，一路生成整段话。

**问题**：第一句已是完美的定义（44 字，理想长度），但紧跟的例子把整段拉到 130+ 字，超出摘要窗口，摘要引擎可能截断成半句。

**建议**：把定义句独立成段，例子另起一段。

```
大模型是什么？它是一个读过海量文字、专门预测「下一个词该是什么」的程序，
不是存好所有答案的数据库，也不是有人在后台替你回复。

你打出「今天中午我想点一份」，它根据读过的无数句子算出后面最可能跟
「外卖」「盒饭」「炒面」，挑一个接上，再猜下一个，一路生成整段话。
```

第一段 58 字，自带定义 + 排除项，是标准的答案优先（answer-first）写法。**同时建议在这句里补上「大语言模型，LLM」的括注**（见 §3.3），一句话解决摘要优化和变体覆盖两件事。

### 7.3 052「AI 提示词怎么写」— 列表型，改动收益最大

「四段结构」是天然的列表型摘要靶子，但当前 H2「四段结构逐段拆」下面是 4 个独立自然段（角色 / 任务 / 背景 / 格式各一段），**没有任何 `<ol>` 或 `<ul>` 标记**，摘要引擎无法识别为列表。

**建议**：把这 4 段改写成有序列表，每项保持「名称 + 一句话说明」的紧凑形态：

```markdown
1. **角色**：告诉它以什么身份回答，比如「你是带过五年团队的部门经理」。身份决定用词和判断标准。
2. **任务**：一句话说清要它产出什么，动词要具体——写、改、列、对比、打分，而不是「帮我看看」。
3. **背景**：给它必要的处境信息，读者是谁、用在哪、有什么限制。这段最容易被省略，也最影响结果。
4. **格式**：指定输出形态，几段、几条、表格还是清单，多少字。这段决定你拿到手要不要返工。
```

字数几乎不变（现有内容重排即可），但形态从「4 个散段」变成「结构化 4 项列表」，列表型摘要捕获概率显著提升。**这是全批单点收益最高的一处改动。**

### 7.4 039「免费 AI 工具推荐」— 列表型，当前最大的形态浪费

## 十、开头区块关键词规范（会签 content-editor，适用后续 90 篇）

content-editor 提议：「关键词在开头区块自然出现一次即可，H2 携带关键词即满足开头覆盖」。

**SEO 侧结论：接受该方向，但表述必须精确化，否则会漏掉 041 这类情况。** 正式规范如下三条：

### 规则 1（默认）：H2#1 携带关键词 → 首段不必重复

适用对比型、清单型、教程型选题（本批 001/002/009/025/034/039/047/052）。
依据：qa_check 的 130 字窗口从正文起算，**H2#1 完整落在窗口内**（实测 H2#1 归一化长度 15–33 字），关键词在 H2#1 中即已满足开头覆盖。这类选题的目标摘要形态是表格型/列表型，首段并非摘要抽取的主要素材，重复关键词的边际收益接近零，而复读感是实打实的。

**注意：规范措辞必须是「H2#1」而不是「H2」。** qa_check 的 `H2无KW` 检查用的是 `any(...)`，接受任意 H2；但 130 字窗口只覆盖 H2#1 加首段开头约 100 字。两者不等价。

### 规则 2（例外 A）：H2#1 不携带关键词 → 首段前 100 字内必须自然出现一次

触发场景：H2#1 采用「为什么…」「先说结论…」等问题式/铺垫式写法，导致关键词被拆散或插入虚词。

**本批实例 041**：H2#1「为什么 AI 写的小红书文案一眼假」因多一个「的」，归一化后与关键词不匹配，其开头覆盖**完全依赖首段**（落点第 18 字）。若按规则 1 删除首段关键词，qa_check 将报「开头无KW」。

好消息是 qa_check 的 130 窗口检查本身就是这条规则的自动守门员，**无需修改 qa_check**——它已经能精确捕获规则 2 被违反的情况。写作时不必人工判断，跑一遍自检即可。

### 规则 3（例外 B）：定义型/概念型选题 → 首段首句仍应含关键词

适用 what-is-X 类选题（本批 081，后续如「AI Agent 是什么」「多模态是什么」）。

依据：这类选题的目标是**段落型精选摘要**，而段落型摘要是**独立抽取**的——SERP 上展示的往往只有那一段文字，H2 不一定同时呈现。因此答案句必须自足，首句重述主语（「大模型是什么？它是一个……」）既是摘要优化，也是正常的中文行文习惯，不构成复读。

081 当前首段正是标准写法，**请勿按规则 1 精简**。§7.2 的段落拆分建议仍然有效且依赖这一句。

### 一句话总结给写作模具

> 开头区块关键词出现 **1 次**为默认；只有当 H2#1 不带关键词、或选题是「X 是什么」定义型时，才需要在首段再出现 1 次。以 qa_check 跑通为准，不用人工数。
